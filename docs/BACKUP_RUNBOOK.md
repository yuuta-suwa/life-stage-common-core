# BACKUP RUNBOOK｜週1回バックアップ運用手順（Supabase Free）

最終更新：2026-11-19。前提：Supabase は Free プランのまま運用する（D-38）。Free には自動の日次バックアップがないため、本手順の手動バックアップだけが復旧手段になる。

## 1. 対象と対象外

| 対象 | 内容 | 方法 |
|---|---|---|
| ✅ DB：`public`・`private` | 利用者・権限・招待・監査ログ・APP01 の回答・確定履歴・共有・ブループリント・引き継ぎ | `scripts/backup.sh backup`（pg_dump カスタム形式＋SHA-256） |
| ✅ DB：`auth` | ログインアカウント（Google 連携の情報）・MFA 登録 | 同上 |
| ✅ DB：`storage`（メタデータ） | 画像ファイルの一覧（どの利用者のどのファイルか） | 同上 |
| ❌ **画像ファイル本体** | LEVEL03 ビジョンボードの写真 | **pg_dump には含まれない**。§6 参照 |
| ❌ 設定 | Google OAuth・Site URL・MFA 設定、Vercel の環境変数 | 設定値は docs/OPERATIONS.md に記録済み（秘密値は除く） |

## 2. 担当と頻度（案。発注者が決定する：Q-19）

| 作業 | 頻度 | 正担当（案） | 副担当（案） |
|---|---|---|---|
| バックアップ取得 | **週1回**（例：毎週月曜 10:00 までに） | 運用担当者（発注者が指名） | Super Admin（発注者） |
| 取得結果の記録 | 取得のたび | 同上 | — |
| 復元テスト | **月1回**（毎月第1週の取得分）＋手順や DB を変えたとき | 開発担当者 | 運用担当者 |
| 古い世代の削除 | 月1回 | 運用担当者 | — |

試験運用期間（5名）は、上の担当が決まるまで開発担当者が代行してよい。ただし、DB パスワードは発注者が管理する。

## 3. 事前準備（初回のみ）

1. **DB パスワード**：Supabase ダッシュボード → Project Settings → Database で確認する（不明な場合は再設定。アプリはこのパスワードを使わないので、再設定してもアプリへの影響はない）。パスワードマネージャーに保存し、チャット・GitHub・メールに書かない。
2. **接続文字列**：同じ画面の「Connection string」から **Session pooler** を使う（IPv4 環境で接続できる）。
3. **PostgreSQL 17 以上のクライアント**（`pg_dump`・`pg_restore`・`psql`）。サーバーは Postgres 17 のため、クライアントが古いと失敗する。
4. **保管先**（§5）を用意し、暗号化のパスフレーズをパスワードマネージャーに保存する。

## 4. 手順

### 4-1. 取得（毎週）
```bash
read -s SOURCE_DB_URL && export SOURCE_DB_URL   # 接続文字列を貼り付け（画面・履歴に残さない）
OUT_DIR=./backups bash scripts/backup.sh backup
# → backups/lsc-YYYYMMDDTHHMMSSZ.dump と .sha256 ができる
```
取得後、すぐに暗号化して保管先へ移す（§5）。作業 PC にはファイルを残さない。

### 4-2. 復元テスト（毎月）
空の検証用 DB に復元し、件数を元の DB と比べる。**本番 DB を復元先に指定しない**（スクリプトは同じ URL を拒否する）。
```bash
# 例：ローカルの PostgreSQL 17（または docker の postgres:17）に空の DB を作る
createdb lsc_restore_check
export VERIFY_DB_URL=postgres://postgres@127.0.0.1:5432/lsc_restore_check
bash scripts/backup.sh verify backups/lsc-YYYYMMDDTHHMMSSZ.dump
# → SHA-256 OK、各テーブルの件数（APP01 含む 12 項目）が一致すれば「VERIFY OK」
dropdb lsc_restore_check   # 確認後に削除（復元先にも個人データが入るため）
```
取得から時間が空くと、本番側で増えた行の分だけ「VERIFY DIFF」になる。取得直後に実行するか、差分が「増えた分だけ」であることを目視で確認する。

### 4-3. 記録（毎回）
`docs/BACKUP_LOG.md`（または発注者指定の台帳）に次を残す。

| 日時 | 種別 | ファイル名 | SHA-256（先頭12桁） | サイズ | 結果 | 担当 | 備考 |
|---|---|---|---|---|---|---|---|
| 2026-11-19 | 復元テスト（ローカル検証DB） | lsc-20261119T090143Z.dump | — | 167KB | VERIFY OK | 開発 | 手順確認用。本番データではない |

## 5. 保管先（案。発注者が決定する：Q-20）

- **推奨**：発注者が管理する Google ドライブの共有ドライブ（またはフォルダ）。アクセスできるのは発注者と運用担当者だけにする。
- **必ず暗号化してから置く**（ダンプには個人の回答本文が含まれる）。
  ```bash
  gpg --symmetric --cipher-algo AES256 backups/lsc-YYYYMMDDTHHMMSSZ.dump   # .dump.gpg ができる
  ```
  パスフレーズはパスワードマネージャーに保存し、ファイルと同じ場所に置かない。
- **置かない場所**：GitHub、個人 PC のデスクトップ（暗号化なし）、メール添付、チャット。
- **保持世代**：週次は直近 **4 世代**（約1か月）＋月初分を **3 か月**。それより古いものは削除する。退会者のデータもこの期間でバックアップから消える（アカウント削除の説明と整合させる：Q-05）。

## 6. 画像ファイル本体（ビジョンボード）について

pg_dump では画像本体は取得できない。試験運用（5名）では次の扱いを推奨する。
- **推奨（試験運用）**：画像はバックアップの対象外とし、障害時は本人に再アップロードを依頼する（元の写真は本人の端末にある）。この点を試験参加者への案内に書く。
- **正式運用で必要なら**：Supabase の「S3 互換アクセスキー」を発行し、`rclone` 等で `user-files` バケットを週1回コピーする。アクセスキーは秘密情報のため、発行・保管は発注者の承認が必要。

## 7. 復旧手順（障害時）

| 状況 | 対応 |
|---|---|
| 誤操作で一部のデータが消えた・壊れた | 1) 影響範囲を監査ログで確認 → 2) 最新のバックアップを**検証用 DB** に復元（4-2）→ 3) 必要な行だけを確認したうえで戻す。本番への書き戻しは発注者の承認後に開発担当者が行う |
| プロジェクト全体が使えない | 1) 新しい Supabase プロジェクト（東京）を作成（要承認）→ 2) `supabase/migrations` を順に適用 → 3) バックアップを復元 → 4) Google OAuth・Site URL・MFA を docs/OPERATIONS.md のとおり再設定 → 5) Vercel の環境変数を新プロジェクトの URL・公開キーに変更 → 6) 受入スモークテスト |
| Free の自動休止（7日間利用なし） | ダッシュボードで「Restore」を押すと再開する（データは保持）。再開後に通常どおりバックアップを取得する |

> 「プロジェクト全体の復旧」は手順の検証を**ローカル環境でのみ**実施した。実 Supabase の新プロジェクトへの復元は、プロジェクトの追加作成（承認が必要）を伴うため未実施。

## 8. 失敗時の対応

| 症状 | 原因の例 | 対応 |
|---|---|---|
| `pg_dump: connection ... failed` | パスワード違い・Direct 接続（IPv6）を使っている・プロジェクトが休止中 | Session pooler の接続文字列を使う。休止中なら再開してから取得 |
| `server version mismatch` | クライアントが Postgres 16 以下 | PostgreSQL 17 のクライアントを使う |
| `sha256sum: WARNING ... did NOT match` | ファイルの破損・転送失敗 | そのファイルは使わない。取り直す |
| `VERIFY DIFF` | 取得後に本番で行が増えた／復元漏れ | 増えた分だけなら記録して可。減っている・0 件なら失敗として扱い、取り直して再検証 |
| `pg_restore: error` | 復元先が空でない・権限不足 | 新しい空の DB を作り直して再実行 |
| 予定日に取得できなかった | 担当不在など | 気づいた時点で取得し、記録の備考に遅延を書く |
| **2 週続けて失敗**、または復元テストが失敗 | — | 開発担当者に連絡。原因が解消するまで試験運用の新規入力を控えてもらうか、Pro プラン（日次自動バックアップ）を検討する（要承認） |

## 9. 2026-11-19 の検証結果

- `backup.sh` で取得 → 空の DB へ復元 → 件数の比較：**VERIFY OK**。復元先でも RLS が 23/23 テーブルで有効、関数 63 個を確認した（ローカル PostgreSQL）。
- 検証で見つけた不具合：新しい空の DB への復元が `schema "public" already exists` で失敗していた。`--clean --if-exists` で修正済み。比較対象に APP01 のテーブル・auth・storage を追加した。
- 自動テスト AT20（`tests/db/backup.test.ts`）：全業務テーブル（APP01 含む）の件数と内容ハッシュが復元前後で一致。
- **未実施**：実 Supabase からの取得（DB パスワードが必要。発注者の作業または共有が必要：R-12）。
